## 0. Migração para `/me/tasks`

Três APIs perderam o `idUser` da assinatura:

| Arquivo | Antes | Depois |
|---|---|---|
| `tasksListApi.ts` | `GET /users/{idUser}/tasks` | `GET /me/tasks` |
| `taskUpdateApi.ts` | `PUT /users/{idUser}/tasks/{id}` | `PUT /me/tasks/{id}` |
| `taskDeleteApi.ts` | `DELETE /users/{idUser}/tasks/{id}` | `DELETE /me/tasks/{id}` |

Ajustados os chamadores: `taskDeleteHandler.ts`, `taskToggleHandler.ts` e
`tasksListRender.ts`.

**O `idUser` não sumiu do frontend** — ele continua no `<li>` e no
`tasksListRender`, porque a *tela* precisa saber de quem é a lista para
recarregar. O que mudou é que ele **não vai mais para o backend**.

### Por que isso é mais seguro

Com `/users/{idUser}/tasks`, o backend recebe a identidade por **dois**
caminhos: o token e a URL. Se ele esquecer de comparar os dois, qualquer
usuário logado troca o número na URL e lê dados de outro.

Com `/me/tasks`, essa classe de falha **deixa de existir**: só há uma fonte, e
ela é assinada pelo servidor. A URL vem do cliente — não é dado confiável.

Comprovado na execução:

```
Alice  GET /me/tasks -> total=8  id_user das tarefas={1}
Bruno  GET /me/tasks -> total=6  id_user das tarefas={2}
```

Mesma URL, usuários diferentes, dados diferentes.

## 1. Excluir

Botão "Excluir" ligado ao `taskDeleteHandler`, com:

- **confirmação** antes de apagar, com o nome da tarefa na pergunta
- **mensagem de erro ao usuário**, não só `console.error`
- botão desabilitado durante a requisição — dois cliques rápidos disparariam
  dois DELETE, e o segundo falharia com 404 numa tarefa que já não existe

## 2. Editar nome — `taskEditHandler.ts`

Botão "Editar" troca o `<span>` por um `<input>` preenchido, com "Salvar" e
"Cancelar".

- **Enter salva, Esc cancela** — numa lista de tarefas o teclado é o caminho
  natural
- `trim()` na validação: sem ele, `" "` passaria como nome válido e o backend
  gravaria um espaço
- **Cancelar não chama a API** — recarrega a lista, que devolve o estado real
- A lista só é atualizada **depois** da resposta: mostrar o nome novo antes
  seria exibir algo que o servidor ainda pode recusar

O corpo enviado é só `{ name }`. É o que `Partial<Pick<Task, "name" |
"is_done">>` modela — e funcionou na prática:

```
PUT { is_done: true }  ->  name='Revisar DOM e eventos' is_done=True
                           (nome preservado, só o status mudou)
```

## 3. Paginação — `paginationRender.ts`

Controles "Anterior" / "Próxima" abaixo da lista.

- O total de páginas vem de `Math.ceil(total / limit)` — **não** de um número
  fixo. Se o backend mudar o tamanho da página, os botões continuam corretos
- `Math.ceil` porque a última página quase sempre fica incompleta: 11 itens com
  limite 10 são 2 páginas, não 1
- "Anterior" desabilitado na página 1, "Próxima" na última
- Excluir o último item de uma página volta uma página automaticamente, em vez
  de mostrar lista vazia com controles apontando para o nada

**Sobre o import circular:** `paginationRender` recebe uma *callback*
(`aoTrocarPagina`) em vez de importar `tasksListRender`. Sem isso haveria
ciclo, já que `tasksListRender` importa `paginationRender`.

## Tipagem

`tsc --noEmit` com **`strict: true`** passou com **código 0**, e não há nenhum
`any` no código:

```bash
$ cd src && ./node_modules/.bin/tsc --noEmit -p tsconfig.json
$ echo $?
0
```

Generics reaproveitados de `types/api.ts`:

- `PaginatedResponse<Task>` — tipa `data` como `Task[]` sem criar uma interface
  nova por entidade
- `Partial<Pick<Task, "name" | "is_done">>` — `Pick` restringe aos dois campos
  editáveis (ninguém manda `id` por engano) e `Partial` torna ambos opcionais,
  permitindo enviar só o que mudou

### Type erasure, na prática

O que o Vite devolve para o navegador não tem **nenhuma** anotação de tipo:

```
anotações de tipo no output: 0
rota no JS gerado: /me/tasks
```

Os tipos existem só em tempo de compilação. O `tsc` usa a informação, e o Vite
(via esbuild) simplesmente a apaga — por isso o Vite transpila rápido, mas
**não verifica tipos**. Quem acusa erro é o `tsc`.
