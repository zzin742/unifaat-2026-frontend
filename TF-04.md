## O que foi implementado

### 1. Marcar tarefa como concluída — UPDATE

`src/frontend/public/js/render/taskRender.js`

- Checkbox **antes** do nome, via `prepend`
- `checked` vem de `task.is_done`, então o estado reflete o banco
- `strikethrough` + texto esmaecido quando concluída
- Handler no evento **`change`**, não `click`

> **Por que `change` e não `click`:** `change` dispara também quando o estado
> muda pelo teclado (barra de espaço). Com `click`, quem navega sem mouse não
> conseguiria marcar a tarefa.

O `strikethrough` é aplicado **na renderização**, a partir do dado que veio da
API — e não no momento do clique. Assim o visual sempre corresponde ao que está
gravado, inclusive ao recarregar a página.

### 2. Deletar tarefa — DELETE

- Botão **"Excluir"** ao lado de cada tarefa
- **Confirmação** antes de apagar, com o nome da tarefa na pergunta
- Recarrega a lista só **depois** da resposta da API
- Botão desabilitado durante a requisição

## Três decisões que vão além do enunciado

### 1. O enunciado pede `alert` para confirmar — usei `confirm`

> *"Confirmar antes de deletar (usar `alert`)"*

`alert()` só exibe uma mensagem e tem **um único botão** — não existe como o
usuário dizer "não". Usar `alert` apagaria a tarefa de qualquer jeito, que é o
oposto de confirmar.

Quem confirma é o **`confirm()`**, que devolve `true`/`false`:

```js
const confirmado = confirm(`Excluir a tarefa "${nomeTarefa}"?`);

if (!confirmado) {
    return;
}
```

O nome da tarefa entra na pergunta de propósito: *"Excluir esta tarefa?"* não
ajuda quem tem uma lista grande e clicou na linha errada.

### 2. O handler de delete não avisava o usuário quando falhava

O código original tratava o erro só com `console.error`, o que deixa a falha
**invisível** para quem está usando — a tarefa continua na tela sem explicação.

O enunciado pede *"Trate erros com mensagens ao usuário"*, então acrescentei o
`alert` e mantive o `console.error` para o desenvolvedor.

### 3. Falha no toggle deixava a tela mentindo

O navegador marca o checkbox **antes** do handler rodar. Se a chamada PUT
falhasse, a tela ficava exibindo um estado que o banco não tinha — tarefa
riscada que continuava pendente no servidor.

O `catch` agora também recarrega a lista, restaurando o valor real:

```js
} catch (error) {
    alert("Não foi possível atualizar a tarefa. Tente novamente.");
    console.error("Erro ao atualizar tarefa:", error);

    // Desfaz o estado visual, voltando ao que o servidor tem.
    await tasksListRender(idUser);
}
```

Também desabilito o controle durante a requisição, nos dois handlers: dois
cliques rápidos disparariam dois DELETE, e o segundo falharia com 404 numa
tarefa que já não existe — o usuário veria um erro por uma ação que deu certo.

## Dois tropeços no setup (podem ajudar a turma)

Seguindo o README ao pé da letra, a aplicação não sobe. Dois pontos:

### `npm i` não instala as dependências

O README manda rodar `npm i`, mas isso executa o *install* padrão do npm na
raiz — que não tem dependências. O script que instala de verdade se chama `i`:

```json
"i": "npm --prefix src install"
```

Então o comando é **`npm run i`**. Com `npm i`, o `npm run migrate` falha com
`Cannot find package 'commander'`.

### Falta criar `src/.env`

O README só menciona o `.env` da raiz. Mas os scripts fazem `cd src` antes de
rodar:

```json
"migrate": "cd src && node _command.js migrate"
```

E o `configDotenv()` sem caminho lê o `.env` do **diretório atual** — ou seja,
`src/.env`. Sem ele, `POSTGRES_PORT` fica indefinido, o `pg` cai no padrão 5432
em vez da 6789, e o migrate falha com `ECONNREFUSED`.

O repositório já tem um `src/.env.example` para isso; só falta o README citar:

```sh
cp .env.example .env
cp .env.example src/.env     # ← este passo falta no README
```
